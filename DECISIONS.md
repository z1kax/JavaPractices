# Принятые проектные решения

В данном файле описаны ключевые технические решения, принятые при выполнении практических работ 5-8. Основной упор сделан на соблюдение бизнес-правил, инкапсуляцию и защиту данных.

## ПР5. Строки и массивы (TimesheetAnalyzer)
1. Обработка ошибок парсинга: Для преобразования строк в числа используется Integer.parseInt внутри блока try-catch. Это позволяет перехватить NumberFormatException и вернуть понятное сообщение с указанием конкретной позиции (дня недели), а не просто уронить программу.
2. Вычисление среднего: При расчете среднего значения используется явное приведение к double ( (double) sum / 5 ). Это необходимо, чтобы избежать целочисленного деления, при котором дробная часть отбрасывалась бы.
3. Разбиение строки: Используется split(";"). Если строка приходит с лишними пробелами, они удаляются через trim() перед парсингом.

## ПР6. Маршрутизация (ApprovalRouter)
1. Приоритет правил: Порядок проверок в методе route строго определен. Сначала проверяется наличие персональных данных (SECURITY_REVIEW), затем высокий риск (DIRECTOR_REVIEW), и только потом сумма и срочность. Это гарантирует, что более слабое правило (например, FAST_TRACK) не перекроет более строгое (безопасность).
2. Пороговые значения: Лимит для финансового согласования (500 000) вынесен в public static final константу FINANCE_LIMIT. Это упрощает поддержку кода, если бизнес-правило изменится.

## ПР7. Корпоративный заказ (ООП)
1. Защита внутренней коллекции: В классе Order метод getItems() возвращает Collections.unmodifiableList(items). Это сделано для того, чтобы внешний код не мог напрямую добавить или удалить позицию в обход бизнес-логики (например, после подтверждения заказа). Изменять состав можно только через метод addProduct.
2. Объединение повторных товаров: При добавлении товара в заказ сначала проверяется, есть ли уже такой товар по id. Если есть, то новое количество прибавляется к существующему через setQuantity, а не создается дублирующая строка.
3. Расчет итоговой стоимости: Метод total() не хранит итоговую сумму в отдельном поле, а вычисляет её каждый раз на основе текущего списка позиций. Это исключает рассинхронизацию данных, если состав заказа изменился.

## ПР8. Управление состоянием (BusinessTrip)
1. Отказ от сеттеров: Публичного метода setStatus() нет. Состояние командировки меняется только через бизнес-методы (submit, approve, reject и т.д.). Это защищает объект от некорректных переходов (например, нельзя перевести поездку из DRAFT сразу в COMPLETED).
2. Валидация причины отклонения: Метод reject принимает строку с причиной. Перед изменением статуса выполняется проверка, что причина не пустая и содержит минимум 10 символов. В случае ошибки выбрасывается IllegalArgumentException.
3. Проверка даты завершения: Метод complete проверяет текущую дату через LocalDate.now(). Если командировка еще не закончилась, выбрасывается IllegalStateException.
